Analysis Questions

### 1. Differentiate Task and Data Parallelism. Identify which part of the lab demonstrates each and justify the workload division.
- Task Parallelism and Data Parallelism differ in what runs concurrently: Task Parallelism executes different operations on the same data, while Data Parallelism applies the same operation to different data. Part A demonstrates Task Parallelism by computing four different deductions (SSS, PhilHealth, Pag-IBIG, Tax) concurrently on a single employee's salary, dividing the workload by task type where each thread handles one deduction calculation. Part B demonstrates Data Parallelism by applying the complete payroll computation function to all five employees simultaneously, dividing the workload by data where each process handles one employee's entire calculation independently.

### 2. Explain how concurrent.futures managed execution, including submit(), map(), and Future objects. Discuss the purpose of with when creating an Executor.
- The concurrent.futures module manages execution through Executors that schedule and run tasks concurrently, where submit() schedules individual tasks and immediately returns a Future object representing the eventual result that can be retrieved using result(), while map() applies a function to multiple items in parallel and returns results in order. Future objects act as placeholders for results that may not be available yet, allowing the program to continue executing while waiting for task completion. The with statement ensures proper resource management by automatically shutting down the executor and cleaning up threads or processes when the block completes, preventing resource leaks even if errors occur.

### 3. Analyze ThreadPoolExecutor execution in relation to the GIL and CPU cores. Did true parallelism occur?
- ThreadPoolExecutor does not achieve true parallelism for CPU-bound tasks due to Python's Global Interpreter Lock (GIL), which allows only one thread to execute Python bytecode at a time regardless of the number of CPU cores available. In our lab, the deduction calculations are simple CPU-bound operations that complete so quickly that threads were reused rather than running simultaneously, as evidenced by the same thread (ThreadPoolExecutor-0_0) executing multiple tasks sequentially. True parallelism did not occur because the GIL prevented multiple threads from computing deductions at the exact same moment, though the tasks were scheduled concurrently and could have overlapped during I/O operations if any existed.

### 4. Explain why ProcessPoolExecutor enables true parallelism, including memory space separation and GIL behavior.
- ProcessPoolExecutor enables true parallelism because it creates separate Python interpreter processes rather than threads, where each process has its own memory space and its own GIL, allowing multiple CPU cores to execute Python code simultaneously without interference. Since each employee's payroll computation runs in a completely independent process with isolated memory, the GIL in one process does not block execution in another process, enabling all five employees to be genuinely processed at the same time across multiple CPU cores. This memory separation means processes cannot share data directly and must communicate through serialization, but it eliminates the GIL bottleneck that prevents ThreadPoolExecutor from achieving true parallel execution for CPU-intensive tasks.

### 5. Evaluate scalability if the system increases from 5 to 10,000 employees. Which approach scales better and why?
- Data Parallelism with ProcessPoolExecutor scales significantly better for 10,000 employees because it distributes independent computations across multiple processes that can fully utilize all CPU cores simultaneously, whereas Task Parallelism would still process employees one at a time, only parallelizing the four deductions per employee. With 10,000 employees, Data Parallelism can process hundreds or thousands concurrently (limited by CPU cores), completing all payroll in minutes, while Task Parallelism would sequentially process each employee taking hours. However, the optimal solution would use a process pool with a worker count matching the number of CPU cores (typically 4-16) rather than creating 10,000 processes, as excessive processes cause memory overhead and context-switching delays that actually decrease performance.

### 6. Provide a real-world payroll system example. Indicate where Task Parallelism and Data Parallelism would be applied, and which executor you would use.
- In a real-world payroll system processing 50,000 employees, I would use Data Parallelism with ProcessPoolExecutor as the primary approach to distribute employee payroll computations across multiple CPU cores, processing batches of employees simultaneously to complete the entire payroll efficiently. Within each employee's calculation, I could apply Task Parallelism with ThreadPoolExecutor for I/O-bound operations such as concurrently fetching tax rates from a database, retrieving attendance records from an API, downloading timesheet data from cloud storage, and validating employee information against external systems. For example, while Process 1 calculates Alice's payroll using threads to fetch her data, Process 2 simultaneously calculates Bob's payroll, Process 3 handles Charlie's, and so on across all available CPU cores, combining both parallelism types to optimize both CPU-intensive calculations (processes) and I/O-waiting operations (threads).
